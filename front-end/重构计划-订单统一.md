# 重构计划 · 订单系统统一（阶段一）

> 目标：取消「任务/服务」的双轨制，全系统统一为 **付款方(payer) / 收款方(earner)** 两角色、一套订单、一个发布页、一套评价机制。
> 范围：**阶段一（B 方案）**——只做主重构；`disputed`/`closed`（争议/管理员）这一阶段**只在状态枚举里预留位置**，不实现管理员功能（留作阶段二）。
> 原则：每一步都能独立在浏览器里验证，改坏了能单步回退，不一次性铺开。

---

## 0. 开工前准备

1. **建分支**：在 `front-end` 当前分支基础上新建 `refactor/unified-order`，每完成一个 Step 提交一次，方便回退。
2. **验证习惯**（贯穿全程）：本项目是静态站、mock 数据存在 localStorage。每次验证前若涉及数据结构变化，先在浏览器 DevTools Console 执行 `localStorage.clear()` 再刷新，避免旧数据干扰。
3. **新增一个常量**：在 `mock-data.js` 顶部加 `const AUTO_DAYS = 2;`（自动确认 + 评价窗口共用同一天数）。

## 目标数据模型（先看终点，再分步走）

### 帖子（沿用 `db.tasks` 这个数组名，减少改动面；语义改为「帖子/需求」）
| 字段 | 变化 |
|------|------|
| `type: demand\|service` | **删除**，换成 `publisherSide: 'payer'\|'earner'`（发布者出钱还是收钱）。映射：demand→payer，service→earner |
| `status` | 统一为 `'open'`（大厅可接） / `'closed'`（已被接/下架）。订单生命周期不再记在帖子上 |
| `takerId/takerName` `paymentStatus` `publisherConfirmed/takerConfirmed` | **删除**，全部迁到订单上 |
| `category` `reward/rewardValue` `publisherId/Name/Credit` `images` `contact` `publishTime` | 保留 |

### 订单（新增 `db.orders` 数组，吃掉旧 `serviceOrders` + 帖子上的订单字段）
```
{
  id, postId, chatId,
  payerId, earnerId,          // 创建时按 publisherSide + 谁响应算出
  amount,
  status,                     // pending|in_progress|completed|cancelled|disputed|closed
  payerConfirmed, earnerConfirmed,
  createdAt, acceptedAt, completedAt,
  autoConfirmAt,              // 一方确认后 = now + AUTO_DAYS
  reviewDeadline              // completedAt + AUTO_DAYS
  // 阶段二预留：disputeReason, disputedBy, resolution{earnerPayout,payerRefund,adminId,note}
}
```
> `disputed` / `closed` 两个状态值**现在就写进注释和枚举**，但阶段一没有任何转换会进入它们。

### 评价（沿用 `db.reviews`）
- 新增 `auto: boolean`，标记"超时系统默认好评"。

### 状态机（阶段一实际启用的部分）
```
帖子(open) ──响应者接单/下单──► pending ──拒绝/撤回──► cancelled
                                  │
                     发布者接受    │ ►冻结付款方, 帖子→closed
                                  ▼
                            in_progress ──双方确认 / autoConfirm到点──► completed
                                                                        ►划款给收款方
                                                                        ►开评价窗口(reviewDeadline)
       (disputed/closed 阶段二接入)
```

## 分步实施

### Step 1 — 数据层：mock-data.js
**做什么**
- 加 `AUTO_DAYS` 常量。
- 改 `createInitialData()` 的种子数据：
  - 每条 task 把 `type:'demand'`→`publisherSide:'payer'`、`type:'service'`→`publisherSide:'earner'`；删除 `paymentStatus/publisherConfirmed/takerConfirmed/takerId/takerName`；`status` 改成 `'open'` 或 `'closed'`。
  - 把现有 `serviceOrders` 种子 + 原本用 task 表达的"进行中的需求单"统一改写进新的 `orders` 数组（payerId/earnerId 按规则填）。
  - `reviews` 种子加 `auto:false`。
  - 返回对象里 `serviceOrders` → 改名 `orders`。
**验证**：Console 跑 `localStorage.clear()` 后刷新任意页，`getDB()` 检查结构：有 `orders`、无 `serviceOrders`、task 有 `publisherSide`。

### Step 2 — 业务层：api.js（核心）
**做什么**（把两套接口合并成一套）
- `publishTask` + `publishService` → 合并为 `publishPost(data)`（data 带 `publisherSide`）。
- 订单接口（取代 takeTask/confirmTaskComplete + createServiceOrder/confirmServiceOrder/getActiveOrder/getOrderHistory）：
  - `createOrder(postId, chatId)`：响应者发起 → 算 payer/earner → `pending`。
  - `acceptOrder(orderId)`：发布者接受 → 校验付款方余额并**冻结** → `in_progress`、帖子 `closed`。
  - `cancelOrder(orderId)`：`pending`→`cancelled`。
  - `confirmOrder(orderId)`：置调用者自己的确认标志；首个确认时设 `autoConfirmAt`；两标志都真 → `completed`、划款、设 `reviewDeadline`。
  - `getOrder(chatId)` / `getOrderHistory(chatId)`。
  - **自动确认**：在读订单的函数里惰性判断 `in_progress && now≥autoConfirmAt` → 自动 `completed`。
- `getTasks(filters)`：按 `publisherSide` 过滤（替代 type），只返回 `open` 帖子。
- 个人数据：`getMyPosts()`（我发布的）+ `getMyOrders(moneyRole)`（我付款的/我收款的），取代 getMyTasks/getMyPublishedTasks/getMyServiceOrders/getOrderCenterRecords。
- 评价：`submitReview` 保留；新增惰性 `ensureDefaultReviews()`——读取时发现 `completed && now≥reviewDeadline && 某方未评` → 补一条 `rating:5, auto:true`（`closed` 订单不补、不计分，阶段一无 closed 故暂不触发）。
- `USE_MOCK` 真实 fetch 分支同步改 URL/字段（先保证 mock 跑通即可）。
**验证**：Console 直接调用，例如 `createOrder('t3','ctest').then(console.log)`，逐个接口验证返回与 `getDB().orders` 变化、余额冻结是否正确。

### Step 3 — 发布页合并
**做什么**
- 新建/复用 `publish-task.html` 为唯一发布页：顶部加二选一 `我出钱(payer) / 我收钱(earner)`，下面分类+标题+描述+金额+图片+联系方式（earner 可加"可服务时间"）。**删除 `take-task.html`**。
- `main.js` `NAV_ITEMS`：把"发布任务""发布服务"两项合并为一项"发布互助"。
- `initPublishForm()`：读 `publisherSide` 单选 → 调 `publishPost()`。
**验证**：两种身份各发一条，回大厅能看到。

### Step 4 — 互助大厅
**做什么**
- `task-hall.html`：类型筛选 `需求单/服务单` → `我能赚钱的(别人出钱)/我要花钱的(别人收钱)/全部`。
- `initTaskHall()`：卡片加身份徽标（悬赏求助·出X元 / 提供服务·收X元）；按钮按 `publisherSide` 切换（`接单赚钱` / `下单找他`）。
**验证**：徽标、筛选、按钮文案随帖子类型正确变化。

### Step 5 — 聊天页（最难，单独一步）
**做什么**：`initChatDetail()` 从按 4 角色分支，重写为「先取本会话订单 → 判断我是 payer 还是 earner → 按状态显示按钮」。

| 订单状态 | 付款方看到 | 收款方看到 |
|---------|-----------|-----------|
| 无订单 | 发起按钮（下单/—） | 发起按钮（接单/—）|
| `pending` | 等待对方接受 / 撤回 | 接受 / 拒绝（取决于谁是发布者）|
| `in_progress`（未确认） | 已支付X·冻结中 → **确认完成** | 完成后到账X → **确认完成** |
| `in_progress`（己方已确认）| 待对方确认 | 待对方确认 |
| `completed` | **去评价**（钱已结算）| **去评价**（X 已到账）|
| `cancelled` | 已取消（已退款）| 已取消 |

**验证**：用两个测试账号（如张三/李四）跑完整链路：下单→接受→双方确认→完成；再测一条只单方确认、改 `autoConfirmAt` 为过去时间验证自动确认。

### Step 6 — 我的订单 / 我的任务
**做什么**
- `order-center.html`：4 个筛选项 → **2 个**（我付款的 / 我收款的）。
- `initOrderCenter()` 调 `getMyOrders()`；`initMyTasks()` 调 `getMyPosts()`+`getMyOrders()`。
**验证**：两个筛选项列表与实际订单一致，金额/状态/对方显示正确。

### Step 7 — 评价窗口与默认好评
**做什么**
- `initReview()` 基于订单评价；写入 `auto:false`。
- 接入 Step2 的 `ensureDefaultReviews()`：到期未评自动补 5★（`auto:true`），列表显示"（用户未评价，默认好评）"。
- 信用分计算确认把 `auto` 评价计入（阶段一 5★ 全计入）。
**验证**：正常评价生效；把某完成订单 `reviewDeadline` 改为过去时间刷新，确认自动补好评且被标记。

### Step 8 — 清理与收尾
**做什么**
- 全局 grep `demand` / `service` / `\.type` / `serviceOrder` / `consumer` / `provider` / `paymentStatus` / `takerId`，清掉残留死代码与旧分支。
- 删除 `take-task.html`；更新 `代码导览.md` 对应章节。
- `orders.status` 枚举注释里保留 `disputed/closed` 说明"阶段二接入"。
**验证**：清缓存后通跑一遍全流程（发布→大厅→下单→聊天→完成→评价→订单中心），无报错、无死链。

## 风险与回退
- **最高风险**：Step 5（聊天页）和 Step 2（订单状态机）。建议这两步各自单独提交，出问题只回退该步。
- **数据结构变更**：每次改 mock 结构后务必 `localStorage.clear()`，否则旧 `campus_mock_db` 会让你误判"代码没生效"。
- **契约一致**：`createOrder/acceptOrder/confirmOrder` 等接口名与返回格式一旦定下，main.js 多处依赖，改名要全局搜。
